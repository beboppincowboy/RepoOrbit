# Security model (sign-in and sessions)

- **Modes.** Without GitHub credentials the app runs in Demo mode: a fixed, labeled demo identity, no tokens stored, remote writes disabled, and only rows marked `is_demo`. With credentials it runs in real mode and never returns demo rows. Exactly one credential set, or a missing/invalid `TOKEN_ENCRYPTION_KEY` in real mode, stops startup.
- **Sign-in.** OAuth with a single-use `state` (hash stored server-side, also bound to the browser by a cookie) and PKCE. The callback only ever redirects to the configured `APP_URL`; no redirect target is accepted from the request.
- **Sessions.** Opaque random cookie (`HttpOnly`, `SameSite=Lax`, `Secure` over HTTPS); only its SHA-256 is stored. Lifetime is a fixed 7 days from sign-in, never extended by use. Logout deletes the row.
- **CSRF.** Non-GET requests need an `Origin` equal to `APP_URL` and an `X-CSRF-Token` derived from the session token (fetch it from `GET /auth/me`). Missing or wrong values are rejected.
- **Tokens.** User and refresh tokens are AES-256-GCM encrypted at rest. Refresh is serialized per user by a row lock because GitHub rotates refresh tokens and each works once.
- **Responses.** Authenticated responses are `Cache-Control: no-store`. Signed-out requests to the GraphQL API get 401 in real mode.

# Security model (repository access)

- **Source of truth.** Access to a repository is never read from a stored row or from `is_private`. Every read and write asks GitHub, with the signed-in user's own token, and fails closed. One exception: while GitHub cannot be reached, the Repositories page lists the user's own selected rows that were last seen as public (metadata they already saw); private rows need a live check.
- **Visible set.** Reads use one listing per user: their owned repositories plus every repository in their installations (user access intersected with the app). It is reused for 30 seconds and shared by concurrent requests; an incomplete or failed listing is reused for the same window so a rate-limited GitHub is not re-hit on every request. A selected repository missing from a complete listing is denied; missing from an incomplete one it is *unverified* and withheld, never treated as allowed or silently empty.
- **Writes.** Connecting a repository ignores the cache and checks live; it must also be on the user's own personal account. A forged or foreign repository id gets 404, and one user's selection can never be changed by another.
- **Single repositories.** A repository outside the listing (for example someone else's public repository) is checked directly on GitHub. A private repository outside the user's installations is denied.
- **Failures.** A rate limit returns a retry time and withholds content; any other upstream error withholds it with no retry time. GraphQL lists carry `withheld` and `retryAt` so clients never show a withheld list as empty. A 401 from GitHub means the token was revoked: the user's sessions and stored tokens are deleted.
- **Installations.** The setup callback stores an `installation_id` only if it appears in the signed-in user's own installation list; the redirect always goes to `APP_URL`. Stored installations are pruned after a complete listing and are never used as an access decision.
- **Both entry points.** The Go API and the TanStack Start web proxy serve the same handlers behind the same session, Origin and CSRF checks.
- **Stars.** Starring is not an access grant. Each user's latest completed star list is stored whole (replaced in one transaction only after every page was read) with its age; a failed or rate-limited refresh keeps it. Public entries come from the snapshot. Private entries are shown only after a live access check (user access and an Installation) and are otherwise hidden and counted. Following requires the repository to be in the user's own snapshot and a live check, and stores only that explicit choice. Lists check selected repositories the user neither owns nor has installed (followed public stars) directly on GitHub, once per listing window.
- **Webhooks.** `POST /webhooks/github` accepts a delivery only with a valid `X-Hub-Signature-256` (HMAC-SHA256 of the raw body with `WEBHOOK_SECRET`, compared in constant time), a body of at most 1 MiB, and a delivery id. An empty secret rejects everything, and real mode will not start without one. A delivery id is stored once, in the same transaction as its work, and is acknowledged only after commit; a failed store returns 5xx so GitHub can redeliver. Payloads are signals, never data: they are not stored or trusted for metadata, a refresh re-reads GitHub, and ordinary events never import an unselected repository.
- **Invalidation.** Installation, installation-repository, authorization-revocation and repository privatize/delete/transfer events bump a PostgreSQL access epoch before any cleanup, so API and worker processes both see it; it works with no selections or a dead job. Webhooks only ever withhold access. A delayed or replayed installation event cannot restore it; restoration needs a fresh GitHub check with the user token. Undelivered events are not fenced: those are caught by live verification on the next read or refresh.

- **App inventory credentials.** The RSA private key is loaded from `GITHUB_APP_PRIVATE_KEY_FILE` in real mode and used to authenticate app-wide installation inventories for cleanup. Protect the file and mount it read-only; app credentials do not grant viewer access. Inventory failures and suspended installations are indeterminate and cannot establish repository absence.
- **Deletion tombstones.** A signed `deleted` delivery for an issue, issue comment or release stores only the numeric resource id (no content) for a repository with an eligible selection, so the deletion cannot be undone by a stale page. Tombstones are removed with the repository row; they hold no private content.
