# U4 behavior and subunits

Companion to [the repository intelligence plan](2026-11-16-1846-feat-repoorbit-intelligence-plan.md#u4-repository-history-and-synchronization-coverage--phase-2b). The user confirmed decisions 1–10 and requested integration of the proposed U4a–U4d split into the main plan. The main plan now owns the implementation contract through KTD9–KTD12 and U4a–U4d; this document preserves the interview record. No implementation is authorized by this planning update.

## Confirmed behavior

User confirmed decisions 1–3 in the first interview round, 4–7 in the second, and 8–10 in the third:

1. **Delivery boundary.** U4 delivers stored activity evidence, ongoing synchronization, authorized reads, and visible coverage/status. Analytics calculations, charts, and timeline rendering remain U5. U4 must demonstrate the correctness and accessibility of its imported evidence without requiring finished analytics screens.
2. **Historical guarantee.** Initial backfill covers at least the latest 90 days of relevant activity, older open issues and PRs, and older records required to measure responses and reviews correctly. An older PR merged within the window retains its creation timestamp and review evidence; an older open issue needs its comment evidence. Ninety days is not a cutoff for evidence required by metrics. Unsupported historical transitions remain explicitly unknown.
3. **Partial success.** Successfully imported evidence stays readable under current authorization when another resource fails or is throttled. Each resource has its own coverage, last success, and retry/failure status. Unfinished work resumes without duplicate records. Missing evidence never becomes zero activity, and partial completion never implies the whole repository is synchronized.
4. **Coverage boundary.** An initial import fixes its starting boundary at least 90 days before its start. A long-running import retains that boundary and catches up to the present before reporting completion; advancing time cannot silently skip evidence.
5. **Refresh triggers.** Selection starts activity synchronization. Relevant webhooks accelerate updates. Periodic polling repairs missed updates for both public and authorized private repositories, starting with U3's 15-minute cadence and rate-limit handling. Incremental work resumes from checkpoints rather than repeating the full backfill.
6. **Manual refresh.** A selected repository offers “Refresh activity,” which schedules unfinished work and checks for updates without erasing evidence. Repeated requests coalesce into existing work and respect throttling and access checks. Manual refresh does not revive dead jobs; explicit operator requeue retains that role.
7. **Synchronization meaning.** Activity counts as synchronized only when every required resource has completed the agreed backfill and a catch-up pass. Freshness is separate from historical coverage. Resource gaps and failures remain visible after an earlier successful synchronization, and unsupported transitions always retain a gap notice. The public contract must express these distinctions rather than relying on the synchronization flag alone.
8. **Issue-event history.** Backfill closing, reopening, assignment, and label changes within the coverage window wherever GitHub supplies event records. Object creation timestamps establish openings. Preserve actor and source time, distinguishing observation time where source time is absent. Webhooks trigger reconciliation without creating duplicate timeline records for API events. Current state, labels, or assignees never establish unobserved historical transitions. Unavailable history remains a visible gap.
9. **Archived repositories.** Archiving does not end synchronization or make evidence unreadable. Continue refreshing evidence and archived status while an eligible selection exists. Recommendations exclude archived repositories under the existing product contract.
10. **Deleted or unavailable records.** Confirmed deletion removes an issue, comment, review, or release from current projections, retaining only minimal identity information needed to prevent resurrection or duplication. Missing pages, timeouts, or ambiguous access failures are not confirmation of deletion. Repository inaccessibility withholds content and invokes existing access-revocation and private-data cleanup rules.

## Sequential subunits — integrated into the main plan

Each subunit leaves a runnable slice. U4a → U4b → U4c → U4d; U5 starts only after all four are complete. These are delivery boundaries, not four parallel work assignments.

### U4a. Resumable issue synchronization and coverage

- **Result:** Selecting a repository imports real issues, labels, and assignees and exposes honest partial activity coverage.
- **Scope:** Extend the existing credential-scoped GitHub client, queue, selection scheduling, and ingestion handlers. Establish resource checkpoints, fixed initial coverage boundary, source timestamps/identities, atomic page projection/checkpoint commits, catch-up, and independent resource status. Reconcile existing eligible selections at startup. Exclude PR-shaped Issues API records from issue projections. Reuse claim/access fences, credential fallback, pacing, and authorization on reads from the first activity commit.
- **Reach:** Incremental activity migration and SQL/generated database code; GitHub client/fake fixtures; ingestion and selection scheduling; worker registration; access cleanup for new private projections; GraphQL schema/generated models/resolvers and existing status components; API documentation.
- **Acceptance:** Multi-page import resumes after interruption without duplication or checkpoint loss. A replaced worker cannot commit. Revocation during a fetch blocks the private commit and subsequent reads. Missing credentials pause; throttling defers. Older open issues and closed issues relevant to the window are included. Issues are readable while comments/reviews/events remain explicitly incomplete; activity does not claim full synchronization.

### U4b. PRs, reviews, and comment evidence

- **Result:** Stored evidence supports U5's first-response, first-review, contributor, and merge-latency calculations without implementing those calculations.
- **Scope:** Import PRs, submitted review records, and issue-thread comments required for metrics. Retain author/reviewer identity, bot classification, relevant source times, and source links. Include older PRs merged within the window and older open objects; fetch older review/comment evidence when required. Extend resource coverage rather than inferring that an empty partial page means no response or review.
- **Reach:** GitHub readers/fakes; PR/review/comment migrations and queries; ingestion handlers/checkpoints; resource-status API/UI and access cleanup introduced in U4a.
- **Acceptance:** An old PR merged yesterday retains its creation time and earlier reviews. An old open issue retains earlier reply evidence. Pending reviews, bots, and author self-responses remain distinguishable for U5. A failed review/comment stream does not stop issue progress, and insufficient coverage remains explicit. Replaying pages does not duplicate evidence.

### U4c. Published releases and issue-event history

- **Result:** Stored release and issue-event evidence can drive U5's timeline with explicit historical gaps.
- **Scope:** Import published releases and supported closing/reopening/assignment/label events within the agreed window. Use issue creation timestamps as opening evidence. Preserve stable event identity, actor, source time, observation provenance, and GitHub links. Reconcile observations to source events without claiming a historical transition from current state. Extend private projection cleanup.
- **Reach:** Release/event GitHub readers and fixtures; migrations, SQL and generated code; ingestion handlers/checkpoints; resource-status API/UI.
- **Acceptance:** Repeated fetches and webhook-triggered fetches yield one record per source event. Late events preserve source chronology. Unsupported history is reported as a gap. Draft releases do not appear as published activity. Private release permission failure is visible and leaves unrelated streams usable.

### U4d. Continuous reconciliation, manual refresh, and U4 acceptance

- **Result:** All activity streams stay current through relevant webhooks, bounded polling, and a user-visible refresh action; coverage and freshness remain honest end to end.
- **Scope:** Extend signed webhook routing and setup documentation for activity resources; reuse durable acceptance and access invalidation. Add 15-minute activity polling for eligible public/private repositories, preserving per-resource progress and bounded work. Add authenticated, CSRF-protected manual refresh for the viewer's eligible selection; coalesce requests without bypassing pacing or reviving dead jobs. Complete archived-state handling, rename handling by stable repository ID, confirmed-deletion reconciliation, and whole-repository status semantics. Refresh intent arriving during execution must survive completion. Retain existing multi-user eligibility and cleanup rules.
- **Reach:** Scheduler, webhook handling and job eligibility/resumption paths; API/worker wiring; repository command routes; GraphQL/status components and refresh UI; fake GitHub fixtures and PostgreSQL/browser tests; API, operations, security, and GitHub App setup documentation as affected.
- **Acceptance:** Missed webhooks are repaired by polling; repeated manual requests coalesce and a request during execution is not lost. One user's deselection does not stop work another eligible user needs; no eligible selectors means no further remote activity work. An archived repository stays readable and refreshable. Ambiguous 404/access errors never erase evidence or expose inaccessible content. Confirmed deletion removes current content. Full backfill plus catch-up enables synchronized status while timestamps, stale resources, failures, and permanent history gaps remain separately visible. Demo remains clearly labeled sample data.
- **Final verification:** Run relevant automated checks and public/private authorization tests. Separately import a public repository without installation and an authorized private repository; record coverage and throttling behavior. If credentials or consent prevent live checks, report that gap rather than claiming live acceptance. Stop before U5 analytics and timeline rendering.

## Implementation constraints and open verification

- U3d is a prerequisite; its completion is not established by this design interview. The checkout has pre-existing backend changes that must be accounted for before implementation.
- Reuse current queue, GitHub client, authorization, and UI patterns; allocate each migration the next unused version when its subunit is implemented.
- Verify endpoint pagination/filtering, source event identity, deletion evidence, permissions, and webhook subscriptions against current official GitHub documentation during implementation. These are factual API checks, not permission to weaken the confirmed behavior. Unsupported evidence is a visible gap; inability to meet a confirmed guarantee must be raised explicitly.
- Each activity resource must join the existing private-data cleanup and authorized read boundaries as soon as it is stored, rather than deferring security integration to U4d.
- Analytics calculations, charts, timeline rendering, recommendations, and issue-management writes remain outside U4. No new dependency, generic ingestion framework, or extra configuration is proposed.
